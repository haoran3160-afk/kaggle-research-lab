# Lessons behind the workflow

These methodological lessons were extracted from static reasoning, interactive reasoning, resource-management games, and coding-agent experiments. They explain the design; they are not independent experimental proof that this skill improves a new competition.

| Observed failure pattern | Transferable improvement |
|---|---|
| A valid protocol and extensive engineering checks coexist with a weak solution | Establish protocol, strong-reference and real-deployment baselines separately |
| Ranking is optimized while the candidate pool contains no correct answer | Decompose generation coverage, selection loss and execution loss before choosing a mechanism |
| A small panel is already solved by both candidates | Use it for regressions or equal-quality cost comparisons; find appropriate unresolved cases to study new capability |
| A local positive disappears under another order, opponent or production schedule | Compare complete denominators, dependencies, conditions and distributions; retain counterexamples |
| A policy requests useful actions that the engine never executes | Inspect actual effects and the first meaningful divergence, not requested actions or nominal tool success |
| Strong baselines and alternative representations are found late | Search for strong references early, while giving genuinely new representations a bounded complete research cycle |
| Multiple reviewers repeat the same mistaken interpretation | Start independent reviewers from primary artifacts and runnable counterexamples; review count does not prove correctness |
| A passing upper-layer example hides a broken generic helper | Check the changed public contract and affected conditions using the actual implementation |
| An agent receives feedback but does not use it to change production code | Distinguish delivery, execution, semantic repair, full task resolution and transfer; retain the cost of extra opportunities |
| A newly introduced tool is never called | Distinguish tool availability from tool selection; do not optimize invocation frequency as a substitute for correct repairs |
| A local score summary conflicts with native results | Repair result extraction and retain the original scoring evidence; do not change the official scorer |
| State summaries omit the latest run or final submission | Checkpoint outcomes before switching work and recover remote jobs by actual accepted IDs |
| More detail is copied into every scheduled wake-up until old plans return | Keep one current state entry and refresh continuation content when stages change |
| Cross-project histories consume budget or constrain a current competition | Keep project state and agent context scoped; consult a historical lesson only for a concrete present question |
| AI-generated learning materials are counted as user mastery | Evaluate the user's own explanation, code or transfer exercise while research proceeds independently |

Exploration and adoption serve different purposes. An early prototype may be weaker while testing a new capability. Promotion still requires useful complete-system evidence, appropriate confirmation and preservation of the current best solution.

Reliability also needs outcome evidence: distinguish occasional success, repeated success, real infrastructure failures, and an agent's own erroneous or empty output. Compare complete budget strategies rather than selecting a winner from many attempts against a single baseline attempt.

The workflow was shaped by real failures, including optimization waves that did not surpass their original strong baseline. That remains a limitation. Package tests demonstrate implementation behavior; only subsequent complete competition comparisons can establish result superiority.
